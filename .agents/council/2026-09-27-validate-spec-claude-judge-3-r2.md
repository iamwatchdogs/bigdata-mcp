## 1. Restating my R1 position

I returned **WARN / HIGH** on the finding that the load-bearing SSH claim is **fully correct** — RFC 4254 §6.5 defines `exec` as one opaque command string, OpenSSH does `execve($SHELL, ["-c", command])`, asyncssh takes `command: Optional[str]` — so *"the security boundary is input validation, not transport shape"* follows correctly. My objection was that the boundary is **unfinished**: `known_hosts=None` fails **open**, the §11.1 path regex admits `..` (§11.4 diagnoses the ordering but §11.1 never binds it), the observer is a second ungoverned command surface, and Solr's `collection` is an unvalidated path segment — plus two unsourced performance numbers and a `truststore` concurrency hazard.

## 3. Blind spots: what all three judges missed

I read the sections nobody audited. Seven findings, and one retraction.

### 3.1 CRITICAL — §12 runs an SSH command with a caller-supplied argument, and no rule covers it

SPEC.md:566:

> | Logs | `yarn logs -applicationId <id>` **over SSH**. …

`<id>` is the `app_id` from tool 7 `yarn_app` (SPEC.md:297, which carries `include: ["detail","logs","diagnostics"]`) and tool 9. And **"over SSH" means `asyncssh.create_session(command=…)`** — which my R1 established is a single string executed as `execve($SHELL, ["-c", command])`. So:

```
app_id = "x; id"   →   yarn logs -applicationId x; id   →   the remote shell runs `id`
```

**RCE on a shared bastion**, from a tool the spec's own workflow #1 depends on. Three independent reasons no stated control stops it:

1. §11.1 rules 2–4 are all **path and scheme** rules. None is an `app_id` rule.
2. §11.2's closed vocabulary contains only `hdfs dfs` forms, and §2.1's guarantee is written as "Every **HDFS** invocation".
3. §11.1 **rule 5** — "*Fuzz the quoter (hypothesis). **This is the one bug class that is RCE on a bastion host.***" — is the only control that would save this, but **neither §11.1 nor §17.2 states the quoter's scope is wider than HDFS.**

And the caller is an LLM whose inputs include the text of HDFS files it has read, while §19 grounds the read-only mandate in "*OWASP LLM06 mitigation #3*". The spec has adopted the attacker-controls-tool-input model and then left an unsanitised argument on the table.

### 3.2 SIGNIFICANT — §15.1's `keychain:` tier is itself a plugin code-execution registry

SPEC.md audits this exact hazard for §5.2's adapters ("*resolve only adapters named in config*") and misses an identical instance in the credential path. `jaraco/keyring` `keyring/backend.py::_load_plugins()` — verbatim:

```python
for ep in metadata.entry_points(group='keyring.backends'):
    init_func = ep.load()            # executes import-time code
    if callable(init_func):
        init_func()                   # and calls it
```

Its own docstring: *"**Any third-party library may register an entry point** … `plugin_name` can be anything."* Selection is by a numeric `priority` on which "*A higher number indicates the backend has higher priority*." So an installed package gets code execution inside the process holding every secret, at credential-resolution time. §16 ships `password_ref = "keychain:bigdata-edge"` as the default — the registry is on the critical path.

### 3.3 SIGNIFICANT — §15.2's device flow contradicts §9's statelessness invariant

RFC 8628 §3.2: `expires_in` REQUIRED (example 1800), `interval` "*clients **MUST** use **5** as the default*". §3.5: `authorization_pending` → poll at `interval`; `slow_down` → "*the interval **MUST** be increased*"; `expired_token` → "*SHOULD wait for user interaction before*" re-issuing, "*to avoid a flood*".

There is an **unbounded human-latency window** (approve on your phone) and §15.2 forbids holding a poll across it — so **the client retry is the only polling mechanism**. Three consequences:

- **Retry storm.** Every retry in that window is a token-endpoint POST at an LLM's cadence, not `interval`'s. MCP's own spec bounds this — "*Retry the original request … **no more than a few times***", clients "*SHOULD* implement **retry limits**". §15.2 specifies no limit.
- **Orphaned device codes.** A retry after expiry re-issues `device_authorization` → a **new** `user_code`; the user approves A while the server holds B. Every orphan is a live unredeemable credential, and RFC 8628's anti-flood SHOULD is unmet.
- **No carrier.** The pending `device_code` must survive the elicitation — but §9 permits no persistence and §3 kills the process in **4 s**. The spec persists the *refresh* token (not needed mid-flow) and not the *device_code* (needed).

Compounding: "re-exchanged on every server start" + RFC 9700 §4.14.2 rotation + a 4 s kill = a lost rotation write leaves a **consumed, invalidated** RT → next spawn presents it → AS detects replay, revokes the active RT → **permanent lockout on the incident-triage tool**.

### 3.4 SIGNIFICANT — no audience validation on the YARN/Solr bearer token

The token isn't consumed by the MCP server — it's attached as a bearer to `https://rm1.corp:8088` and `https://solr1.corp:8983`. Nothing checks audience. RFC 9700 (BCP 240, Jan 2025) §2.3: "*every resource server is obliged to verify … **If it was not, the resource server MUST refuse to serve the respective request.***" MCP's spec is stricter: "*MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience, according to RFC 8707 Section 2*". One corporate realm, many internal apps → **cross-resource token confusion**. §16 has no `resource` key.

*(Checked and cleared: PKCE is **not** required for the device grant — RFC 8628 §3.4's fields are `grant_type` + `client_id` only, and RFC 9700 has **no** device-grant section. §15.2's silence on PKCE is **not** a defect.)*

### 3.5 SIGNIFICANT — §15.3's redaction list is the wrong kind of list, and §8.2 unsatisfies it

The list is a denylist of **header names**; secrets arrive as **values**. And httpx's most common error path does exactly what §8.2 instructs. `httpx/_models.py:794-818`:

```python
message = "{error_type} '{0.status_code} {0.reason_phrase}' for url '{0.url}'\n" …
# redirect branch adds: "Redirect location: '{0.headers[location]}'"
```

`URL.__str__` is `str(self._uri_reference)` — **not redacted**. So a `base_url` with embedded credentials puts the password in `str(HTTPStatusError)`, and per Judge 2's finding the `Location` header is a live, backend-chosen value. **§8.2's "the specific cause" and §15.3's "never in an error message" cannot both be satisfied**, and no rule says which loses.

### 3.6 SIGNIFICANT — §16's alias resolution is unspecified, and asyncssh honours `ProxyCommand`

`entrypoint = "edge-host-alias"`. asyncssh's `config: DefTuple[ConfigPaths] = ()` — the **default is empty**, i.e. no ssh_config read (safe). But to make an alias work you must pass `config=`, and then `prepare()` does:

```python
self.host   = config.get('Hostname', host)                    # :7405  target overridden
self.tunnel = tunnel if tunnel != () else config.get('ProxyJump')  # :7409
if proxy_command == ():
    proxy_command = config.get('ProxyCommand')                 # :7412-13
#  → await loop.subprocess_exec(_ProxyCommandTunnel, *command) # :422  EXECUTED
```

`~/.ssh/config` is user-writable, and §16 gives the *config file* no permission requirement at all. `Hostname` being overridable means §11.1's fails-closed `known_hosts` guarantee is verified against a host that may not be the configured one.

### 3.7 SIGNIFICANT — httpx strips `Authorization` cross-origin… except HTTP→HTTPS, and never `Cookie`

This is the security half of Judge 2's `f-j2-004`. `httpx/_client.py:546-561`:

```python
if not _same_origin(url, request.url):
    if not _is_https_redirect(request.url, url):
        headers.pop("Authorization", None)   # except direct HTTP→HTTPS
```

So **credit where due**: the YARN HA rm1→rm2 redirect does *not* leak the bearer. But (a) the exemption is **HTTP→HTTPS** — the corporate-proxy pattern — and §16 never forbids `http://`; and (b) **`Cookie` is never stripped**, so §15.2's *fallback* credential ("reuse a session cookie") is **more** exposed than the primary, inverting the spec's own risk ordering. And the redirect target is entirely unvalidated → SSRF primitive.

### 3.8 SIGNIFICANT — the envelope cannot express *which* sub-item failed

`Meta` has `partial: bool` and prose `notes` — **no per-item array**. `hdfs_stat` takes `paths: list[str]`; `yarn_app` takes `include: list[...]`. And §11.3 **hazard 6** already verified the mechanism: "*`-stat` line count ≠ argument count. A missing path produces no line while later paths still print.*" The spec **measured** that positional attribution fails and defined a contract with **no field** to record the correction. §8.1's own rejected-alternative note calls silent partial data "the single worst failure mode for an LLM-facing tool."

### 3.9 Also new (details in the JSON)

- **`file:` mode 0600 is documented, never asserted**; the `file:` syntax is never shown; relative paths resolve against a **client-controlled CWD**; and the *config file* — which names every target and credential ref — has **no** permission requirement, unlike the secret file.
- **§13 + §16 concatenate to `/solr/solr/<c>/query`** (`https://solr1.corp:8983/solr` + `/solr/<c>/query`), and YARN's `base_url` convention differs from Solr's in the same TOML. The "repair" that preserves the shipped config promotes the unvalidated `collection` to sole path controller.
- **§12/§13 specify no HTTP methods** — for Solr, the method is what separates `/query` from `/update`.
- **§10.2's unscoped process count** on a host §10.1 calls "shared" counts co-tenants' JVMs, contradicting §10.3's "*no visibility into other people's jobs*"; and §8.1's required `edge_host` field discloses edge-host capacity **on every turn**.
- **§6.4 × §15.1**: the credential helper's output channel *is* its stdout, no rule requires a pipe, and §6.4's CI test covers one *unauthenticated* request.
- **§17.2's seven rows contain no negative security test at all** — and §20's five criteria have no corresponding rows, including criterion 5 (the path-allowlist refusal).

### 3.10 A retraction I owe the council

My R1 `f-j3-004` asserted `collection = "../admin/..."` reaches the Solr admin API. **That does not hold.** With §13's literal `/query` appended and servlet-container normalisation collapsing the `..` first, it lands on the *container's* admin, not Solr's `/solr/admin`. The finding survives on a **better** mechanism — `collection` isn't restricted from `?`/`&`/`#`, so a caller can inject arbitrary query parameters, **including `shards.tolerant` itself**, overriding the one staleness control §13 calls mandatory. The fix is also stronger: a path **allowlist** (which disposes of `collection` structurally) plus an `solr.allowed_collections` config knob that §16 has nowhere to put. A security review that won't retract an overstated exploit isn't calibrated.

## 5. Confirm or revise

**The consensus holds: WARN / HIGH. But the reason has moved, and I concede seven of eight R1 findings.**

On the merits, the devil's advocate is **right** about the R1 items: they are documentation tightenings of an already-correct posture, and **PASS-with-followups was defensible for those alone.** The meta-argument lands too — items 1 and 2 are genuinely N/A, and "*no-duplicate-effect*" is a distributed-systems term with no referent in a stateless read-only tool.

What defeats it is a fact none of the three briefs covered. **§12:566 executes `yarn logs -applicationId <id>` over SSH with a caller-supplied argument, and the spec's own control that would cover it — §11.1 rule 5, "*the one bug class that is RCE on a bastion host*" — has no stated scope.** That is categorically different from every other finding in this council: not a tightening of a correct posture, but the **absence of a control on a remote-execution surface with a caller-controlled argument.**

And the devil's advocate's strongest structural point — §2.1's "the service principal *is* the actual enforcement*" — is true of HDFS and **false where it is doing the most work**: a read-only *HDFS* service principal constrains `hdfs dfs`, and **nothing in the estate constrains what the `yarn logs` command does on the edge host.** The primary control does not exist for the surface where the control is missing, which is exactly why the inversion argument collapses where it matters.

**Final: WARN, HIGH confidence, unchanged — with one critical added, one of my own findings partially retracted, and a corrected reason for holding rather than for releasing.**
